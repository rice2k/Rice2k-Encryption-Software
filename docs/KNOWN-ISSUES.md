# Rice2k Encryption Software — Known Issues and Bug Register

This is the permanent engineering register for errors, bugs, release blockers, and notable fixes. Do not remove historical entries after they are fixed; change their status to **Fixed** and record the version/commit where appropriate.

## Severity

- **Blocker** — prevents a Beta/RC/Stable release or risks data/security correctness.
- **High** — major feature/security/reliability defect.
- **Medium** — important usability/compatibility defect with a workaround.
- **Low** — cosmetic/documentation/polish issue.

## Fixed / mitigated issues

| ID | Severity | Fixed in | Description / resolution |
|---|---|---|---|
| R2K-IO-001 | High / streaming reliability | 0.6.0-preview.4 stabilization source | Chunk writers for `R2KENC01`, `R2KENC02`, `R2KENC03`, and both Secure Vault mutation paths treated each successful `ReadAsync` call as one complete logical chunk. The .NET stream contract permits short reads before EOF, which could make a writer emit more encrypted chunks than the authenticated length-derived chunk count and cause Rice2k to reject its own output during verification. A shared `ChunkReadHelper.ReadFullChunkAsync` now fills each logical chunk buffer until full or true EOF, all five writers use it, and deterministic tests use a stream capped at seven bytes per read plus a pre-cancelled token case. Runtime Windows/.NET validation is still pending. |
| R2K-FMT-001 | Medium / format validation | 0.6.0-preview.4 stabilization source | `R2KENC01`, `R2KENC02`, `R2KENC03`, and secure-vault entry code used addition-based ceiling division for chunk counts, allowing authenticated lengths near `long.MaxValue` to overflow before comparison. All affected readers and writers now use overflow-safe `length == 0 ? 0 : 1 + ((length - 1) / chunkSize)` arithmetic. File-container writers enforce the same metadata ciphertext ceilings as their readers, authenticated original-name metadata is bounded to filename-only values, recipient headers enforce the metadata limit at write time, and vault manifest encryption enforces its reader-side 16 MiB ceiling. Vault headers/manifests/records also reject empty IDs and missing entry lists. Source-controlled parser tests cover oversized metadata-length headers for v1/v2/v3 and empty vault IDs; the full suite still requires supported Windows/.NET runtime execution before release validation can be claimed. |
| R2K-META-001 | Medium / format semantics | 0.6.0-preview.4 stabilization source | Authenticated key, recovery, identity, and signature payloads could carry structurally invalid identity metadata such as empty GUIDs or unreasonable labels farther into the application than necessary. Key/recovery services now validate authenticated IDs/names before constructing session keys; private/public identity import/export rejects empty identity IDs; detached signatures reject empty signer IDs; and `ManagedKey` / private `Rice2kIdentity` objects enforce non-empty IDs plus bounded labels as defense in depth. Key tests were aligned to assert rejection at the earlier generation boundary. |
| R2K-RECIP-003 | Medium / format correctness | 0.6.0-preview.4 stabilization source | `R2KENC03` encryption accepted caller-created `Rice2kPublicIdentity` records without proving that each fingerprint matched its supplied public keys, did not bound fingerprint length on the writer side, and rejected duplicate fingerprints but not duplicate recipient IDs. Recipient validation now enforces non-empty/bounded fingerprints, recomputes and compares the fingerprint from the public keys, rejects duplicate IDs and fingerprints, and bounds serialized authenticated metadata before encryption/finalization. Source-controlled tests cover mismatched fingerprints, oversized fingerprints, duplicate IDs, and no-output cleanup on rejection. |
| R2K-SIG-002 | Medium / format/persistence correctness | 0.6.0-preview.4 stabilization source | `.r2ksig` verification already rejected signature documents above 128 KiB, but signing did not assert the generated JSON stayed inside that format limit and wrote the temporary signature without an explicit disk flush before finalization. Signing now uses the same signer/fingerprint/filename limits as verification, serializes to UTF-8 bytes, rejects oversized generated documents, flushes the `.partial` file before the final move, and has regression coverage for bounded round-trip output and pre-cancelled cleanup. |
| R2K-TEXT-001 | Medium / format correctness | 0.6.0-preview.4 stabilization source | Text encryption could accept plaintext large enough to generate an `R2KTXT1` token above Decrypt's 16 MiB parser limit, allowing Rice2k to create a token it would later reject solely for size. Encrypt now derives and enforces the maximum UTF-8 plaintext size from the token/base64/authentication-tag overhead before Argon2/encryption and checks the generated-token invariant. A source-controlled oversized-plaintext regression test was added. |
| R2K-KEY-002 | Medium / format correctness | 0.6.0-preview.4 stabilization source | `.r2kkey` and `.r2krecovery` creation could serialize key labels/metadata into ciphertext above the 64 KiB limit enforced by their own importers. Both creation paths now bound serialized plaintext before Argon2/output creation and assert the post-encryption size invariant. Key generation also enforces the 200-character label contract before package work; source-controlled tests cover overlong-name rejection and blank-name normalization. |
| R2K-ID-002 | Medium / format correctness | 0.6.0-preview.4 stabilization source | Identity generation/export could create names or private/public package data outside limits already enforced by public-card/private-package import. Identity names now use one 1–200 character rule across generate/private import/public import/export; private payload and public-card output are bounded before finalization, public-card temp output is flushed before atomic move, and a display-name limit regression test was added. |
| R2K-LOCK-003 | High / credential lifecycle | 0.6.0-preview.4 stabilization source | App Lock configuration/removal performed Argon2 and credential/settings consistency work asynchronously outside MainWindow's safe-exit lifecycle. A normal close could terminate the process mid-transition, and minimize/session/inactivity/manual lock triggers could race a credential being replaced or removed. Settings now exposes an active App Lock operation state; MainWindow waits for that consistency boundary before normal exit; lock requests are deferred and re-evaluated against the final saved credential/settings state; credential temp JSON is flushed before replacement. |
| R2K-SET-005 | Medium / persistence | 0.6.0-preview.4 stabilization source | Application settings used a same-directory temp replacement but did not explicitly flush the temp file before rename, had no defensive input-size bound, and could not be isolated easily in tests. Settings writes now flush to disk before replacement, loads reject empty/over-256 KiB files before parsing, the service accepts an optional isolated test directory, and source-controlled tests cover round-trip/temp cleanup, malformed JSON, normalization, and oversized settings fallback. |
| R2K-VAL-005 | Medium / release tooling | 0.6.0-preview.4 stabilization source | The recommended validation command uses Windows PowerShell, but `Validate-Rice2k.ps1` used `System.IO.Path.GetRelativePath`, which is unavailable in Windows PowerShell 5.1's .NET Framework. | R2K-ONBOARD-002 | Low / accuracy | 0.6.0-preview.4 stabilization source | Replaying the Welcome Tour from Settings always reported “completed” after the dialog closed, even when the user closed it early or completion-state persistence failed. ## Recording a new bug

When a bug is found:

1. Assign the next `R2K-<AREA>-NNN` identifier.
2. Record severity, affected version and reproduction details here.
3. Create/link a GitHub Issue for Blocker/High defects or any item requiring multi-step work.
4. Record whether encrypted/source data can be affected.
5. Add a regression test when practical before marking the bug fixed.
6. Move the entry to **Fixed / mitigated issues** only after the source change exists; do not claim runtime validation until the relevant test/build actually runs.
